# OP 0004: 字节码虚拟机（重新实现）

- **状态**：Accepted（第一切片实现中，2026-11-21）
- **作者**：Oort 设计讨论
- **相关**：[设计笔记 02](../design/02-bytecode-vm-design.md)、[HIR 设计 13](../design/13-hir-design.md)、[OP 0001](0001-feature-layers-and-dialects.md)

## 摘要

Oort 需要一个寄存器式字节码 VM 作为动态方言的高性能后端。早期实现已被**移除**；
本提案记录移除原因，以及在重新实现前必须满足的设计约束。

## 背景：为什么移除旧实现

旧实现在 `src/oort_lang/bytecode/`，约 2000 行，覆盖常量、部分算术与原生调用。
主要问题不是“完成度低”，而是**会静默产生错误结果**：

- `BytecodeGenerator` 对未实现的 visitor 使用 `ASTVisitor` 的默认行为（遍历子节点），
  于是 `if` 不生成跳转（then 分支总是执行）、`while` 只执行一次、
  函数/类体在定义处被内联执行、`def f` 没有创建函数对象。
- `var` 声明只生成初始化表达式，不存储；`print(x)` 因此报 `x` 未定义。
- 一元运算的寄存器释放会回收仍在使用的临时寄存器；调用要求实参恰好相邻，
  没有 MOVE 兜底。
- 布尔/空值指令的格式与操作数约定不一致，会覆写 R0（例如把 `print` 函数覆盖掉）。
- 属性/下标/upvalue 指令要么是 stub，要么读写不存在的 `_obj_dict`。
- 行号表、异常表、upvalue 描述从未填充；错误定位全部落到首行。
- 测试只覆盖数据结构（opcode 常量、常量池、反汇编器），没有任何“编码 → 执行”测试。

结论：在语义尚未稳定时，字节码后端把寄存器分配、闭包布局、异常表等工程复杂度
提前引入，并且因为缺少“未实现即报错”的约束，产生了比不实现更糟的结果。
因此删除整包与相关测试；设计文档保留，作为重新实现的参考。

## 重新实现的前置条件

1. **显式失败**：编译器对所有未实现节点必须抛错，禁止依赖 visitor 的默认穿透。
2. **语义先稳定**：`if`/`for`/`while`/函数/闭包/类、容器、切片、增强赋值在
   树遍历解释器上都有测试并通过后再开始。
3. **独立测试**：先写“AST → 期望字节码”的快照测试，再写“字节码 → 结果”的端到端测试；
   不允许只有数据结构测试。
4. **统一对象模型**：不得另建一套值/属性模型（旧实现的 `_obj_dict` 与解释器不兼容）。
5. **元数据完整**：行号表、局部变量名、upvalue 描述、异常表在第一个里程碑就要生成。
6. **寄存器分配**：明确“实参必须位于 `func, func+1, ...`”的不变量，并提供 MOVE
   兜底；局部变量与临时寄存器的生命周期需有单测。
7. **基准**：先用 benchmark 证明树遍历解释器的瓶颈，再决定投入。

## 设计方向（沿用设计笔记 02）

- 寄存器式（Lua 风格），定长 32 位指令；
- 闭包使用 upvalue（打开/关闭 upvalue）；
- 动态模块使用带标签值，静态模块可生成未装箱代码；
- 行号表与异常表一等公民；
- 与 AST 解释器共享 `Environment` 与对象模型，不重复实现。

## 替代方案

1. **继续使用树遍历解释器**：实现最快，性能有限；当前阶段合理。
2. **直接生成 Python 代码并缓存**：开发快，但无法体现编译原理教学价值。
3. **直接上 LLVM**：需要类型信息与内存模型，过早。

## 实现进展（2026-11-21 第一切片）

- **HIR**：`src/oort_lang/hir/` 线性寄存器 HIR（常量、局部/全局、算术、跳转、
  调用、返回、迭代器、函数定义），动态子集 lowering 与结构校验；未实现节点
  在 lowering 阶段显式抛 `UnsupportedSyntax`。设计见
  [HIR 设计 13](../design/13-hir-design.md)。
- **字节码**：`src/oort_lang/bytecode/` 32 位 ABC/ABx/AsBx/Ax、常量池、
  相对跳转回填、line_table、`Proto`、反汇编；`-t bc` 可查看。
- **VM**：`runtime/bytecode_vm.py` 寄存器帧，复用 Environment/内建/类型/运算符/
  迭代器协议；`-t vm` 执行当前子集。Int 算术/比较/一元快速路径，其余回退
  解释器语义；字面量每次求值重新包装以保持 `is` 的身份语义。
- **约束落实**：调用使用 scratch 区约定；`ITER_NEXT` 展开为两字；
  未支持 opcode/构造显式报错，不做默认穿透。
- **基准**（本机中位数，`benchmarks/test_vm.py`）：fib(15) 解释器 102.45ms →
  VM 18.74ms（5.47×）；loop 10000 178.35ms → 76.23ms（2.34×）。fib(20) 粗测
  约 6.2×。
- **当前范围**：标量、List/Tuple/Set/Dict 字面量、内建容器下标与切片、函数/递归、
  分支、while/for(range/字符串/集合)、局部/全局。属性、类/方法、模块与 core
  方言尚未进入 VM；`-t eval` 仍是默认。
- **后续**：扩大 HIR/VM 子集、完善差分与错误路径测试、再切换默认后端；
  之后是寄存器复用/内联缓存/类型特化等优化。

## 未解决问题

- 闭包捕获与 `for` 循环“每迭代新绑定”的语义如何在 VM 中保持？
  第一切片尚不支持闭包；`for` 循环变量复用寄存器，不承诺捕获语义。
- 异常（`break`/`continue`/`return`）用字节码跳转还是异常表？
  第一切片只支持 `return`（`RET`）；`break`/`continue` 在 HIR 显式拒绝。
- 是否需要 `comptime` 共享同一 VM（见 [OP 0005](0005-type-system.md)）？
  暂不决定，等 VM 子集扩大后再评估。
